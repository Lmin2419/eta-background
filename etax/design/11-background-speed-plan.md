# 11 号方案：后台执行提速——少走弯路、少跑空轮（2026111619 之后）

接手 10 号方案暂缓的第四期（界面操作少几轮）和第五期（系统提示瘦身），按这次真机诊断重新定。动手前先读第 0、2 节和最后的执行守则。

## 0. 结论先说

真机诊断（`Etax-diagnostics-1794889886057`，versionCode 2026111618）里最近一次后台小任务：

| 指标 | 数值 |
| --- | --- |
| 总耗时 | 253 秒（用户中途停止） |
| 模型耗时 | 218 秒（86%），43 轮，平均每轮 5.1 秒 |
| 工具耗时 | 16 秒；最慢的是模型自己要的 `wait`（1.5 秒）、`tap`、`tap_element` |
| 工具调用 | 43 次，**失败 12 次（28%）** |

前一天那次界面任务也一样：226 秒里模型占 201 秒，54 轮，失败 8 次。**慢的不是手机，是来回问模型的次数，而且四分之一的来回是在处理失败。** 对着代码找到的原因：

| 感受 | 代码里的原因 | 对应 |
| --- | --- | --- |
| 每做一步都要「再看一眼」 | 前台点完会自动回看屏幕，把新的 `observation_id` 和节点放进结果的 `after` 里，模型接着就能点（`AgentLocalTools`）。**后台点完只把旧观察作废**（`TaskScreenSession.mutateAndInvalidate`），不回看，模型必须再花一整轮调 `observe_screen`。后台每一步固定两轮。 | 第一期 |
| 「这个不行、那个不行」 | 后台动作前会重新读整棵树，算**整页指纹**（每个节点的文字、位置、焦点、选中状态都算进去），和观察时不一样就拒绝（`OBSERVATION_STALE`）。页面上有时钟、进度、加载圈、角标在变，就几乎每次都被拒。 | 第二期 |
| 同上 | 系统提示鼓励「不依赖中间界面变化的操作可同轮调用」，但后台每个动作都要最新的 `observation_id`，第一个动作一提交就作废——**同一轮的第二个动作必然失败**（`OBSERVATION_MISMATCH`）。连按两次返回键、「输入 + 回车」都会撞上。 | 第一、三期 |
| 同上 | 后台不支持的操作仍在工具目录里：`open_uri`、`wait_for_package`、`open_system_panel`、`type_text` 的 `append` 和 `submit`、`PASTE` 等按键。模型照常去用，失败了再换办法。 | 第三期 |
| 「无障碍树和截图很怪」 | 默认只读树不带图。网页、Flutter、游戏这类页面树几乎是空的，模型要先看空树、再要一次带截图的观察；用截图坐标点又必须带上那一帧的 `frame_id`，带错就 `BACKGROUND_FRAME_STALE`。 | 第三期 |
| 「让模型去等」 | 后台 `wait` 是死等（`awaitRetryDelay`），时长靠模型猜；引擎其实有「等页面静下来」（`screen_wait` 不带文字就是 idle），没用上。 | 第一、三期 |
| 规则多、还互相打架 | 系统提示 7 千多字。界面规则前后台混写，有的已经和后台实际行为矛盾（「after 足够时直接用，不要例行 observe_screen」——后台根本没有可用的 after）。 | 第四期 |
| 改文件慢 | 诊断里 `edit_file` 每次 5.2 秒、`write_file` 2.2 秒，比读文件慢一个数量级。 | 第五期 |
| 不知道失败的是什么 | 运行摘要只记了失败**次数**，没记**原因**，所以这次也只能从代码推。 | 第零期 |

按这次的数字粗估：后台每步少一轮观察（约 20 轮）、失败减半（约 6 轮），同一个任务能从 250 秒左右降到 120 秒上下。以第零期记下的真实数据为准。

## 1. 第零期 · 先把失败原因记下来（和第一期一起出）

- 运行摘要（`RuntimeDiagnostics.runDigest`）加三项：
  - `failure_codes`：失败工具的错误码和次数，取前 5（只记码，不记参数和内容）；
  - `gui_rounds`：用到界面工具的轮数，以及其中**只有观察、没有动作**的轮数；
  - `stale`：`OBSERVATION_*`、`BACKGROUND_FRAME_STALE` 一类的次数。
- 诊断导出照旧带最近 20 次。每一期上线后，请用户跑一两次同类任务再导出，用这些数对比。

## 2. 不要做的事

- **不放弃观察合同**：不让模型凭记忆的坐标连点多步，也不做「按文字盲点」的批量脚本。10 号方案第四期暂缓的原因（同名元素误点）仍然成立。
- **不动前台路径**：前台已经有动作后回看，这次只把后台补齐，前台行为和测试不变。
- **不吞失败**：能在工具层自己解决的（同一个元素换了位置）就地解决；解决不了的照样返回失败和原因，不假装成功。
- **不改引擎协议**：只用现有的 `screen_dump`、`screen_wait`（idle）、`screen_key`、`screen_shot` 组合。确实需要改引擎时，同步 `VDrive.java` 的 `BUILD`。
- 系统提示瘦身**一次只删一类**，真机对比没退化才合入。

## 3. 第一期 ·「后台动作后自动回看」（一个版本）

做法（`TaskScreenSession`）：

1. 动作提交后（成功，或结果不明 `ACTION_OUTCOME_UNKNOWN`），先等页面静下来：`screen_wait` idle，最多 800 毫秒，静了就提前返回；
2. 再读一次树（`screen_dump`，节点上限沿用上次观察），**登记成新的观察**（新的 `observation_id`）；
3. 结果里放 `after`，格式与前台一致（复用 `AgentAfterActionSummary`）：新 `observation_id`、`screen_changed`、包名、精简节点、键盘状态；
4. 回看失败不影响动作结果本身，只是不带 `after`，模型照旧自己观察。

效果：后台每一步从「观察一轮 + 动作一轮」变成「动作一轮」；大部分时候也不用再要 `wait`。系统提示里「after 足够时直接用」这条对后台也成立了。

验收：

- 单元测试（假后端）：动作后结果带新 `observation_id`，下一步用这个 id 能直接点；回看失败时动作结果不变；
- 真机：同一个后台任务，「只有观察的轮数」接近 0，总轮数明显下降。

## 4. 第二期 ·「只核对要点的那个元素」（一个版本）

把 `validateLiveSnapshot` 的整页指纹改成按动作类型核对：

| 动作 | 核对什么 |
| --- | --- |
| 点 / 长按某个节点（`tap_element` 等） | 几何（屏幕、旋转）和包名不变；在当前树里**重新找到同一个元素**（`viewId`、类名、文字或描述一致，位置偏移不超过约 24dp），按它**现在的位置**点 |
| 坐标点 / 滑动 | 几何和包名不变；坐标所在的那块区域没有换成别的元素 |
| 按键、往焦点框输入 | 几何和包名不变 |

找不到同一个元素、或者有多个一样的（无法确定是哪个）才返回 `OBSERVATION_STALE`，并在结果里说明是「目标不见了」还是「目标不唯一」。时钟、进度、角标、加载圈的变化不再导致拒绝。

验收：单元测试覆盖「别处文字变了 → 照常点」「目标挪了一点 → 点新位置」「列表滚了、目标没了 → 拒绝」「出现两个同样的 → 拒绝」。

## 5. 第三期 ·「少走弯路」（一个版本）

- **不支持的别让它试**：后台时，工具说明里直接写明哪些不能用；运行时对后台任务不公开 `open_uri`、`wait_for_package`、`open_system_panel`。能补的补上：
  - `type_text` 的 `submit`：写入后自动按回车（`screen_key` 66）；
  - `type_text` 的 `append`：先读回输入框当前文字，拼好再整体写入；
  - `PASTE`、通知栏、快捷设置等按键：说明里写明后台不支持。
- **空树自动带图**：观察时如果有文字的节点少于 3 个，同一次观察自动附截图（缩放 0.5），不用模型再要一次。
- **按键、往焦点框输入不要求 `observation_id`**：只核对包名和几何，「输入 + 回车」「连按两次返回」可以同一轮发出。
- **`wait` 改成「最多等这么久」**：后台的 `wait` 走 idle 等待，页面静了就提前返回，结果里写实际等了多久。

## 6. 第四期 ·「系统提示瘦身」（原 10 号第五期，风险最高）

1. **先量**：运行摘要里加每次请求的输入 token、缓存命中 token 的平均值，作为基线；
2. **删矛盾**：前后台行为对齐后（第一到三期），把界面规则里前后台分开写、已经过时的句子合并或删掉；
3. **挪位置**：只和某个工具有关的规则（通知历史翻页、去重口径、应用冻结限制、统计时间范围……）挪进那个工具自己的说明，工具没公开时就不占篇幅；
4. 目标：系统提示从 7 千多字降到 4 千字以内。每删一类，在真机上跑第 9 节的固定任务前后对比，有退化就加回去。

## 7. 第五期 ·「文件工具少开几次 Shell」（一个版本）

- 先看 `edit_file`、`write_file` 的实现，数清一次调用开了几次 Root Shell（读、比对、写、回读、算 revision）；
- 能合并的合成一次 Shell 调用完成；目标 `edit_file` 1.5 秒以内、`write_file` 1 秒以内；
- 不改返回格式（改动行、revision）和失败语义。

## 8. 可选实验（默认关，用数据决定）

- **界面操作轮用较低思考强度**：模型支持思考强度时，屏幕操作阶段（拿着操作权或后台屏幕会话期间）的轮次用低一档，回答和规划轮不变。用第零期的「平均每轮模型耗时」和失败率前后对比，没退化才考虑默认开。
