# 10 号方案：底层 Agent 执行——更准、更快（2026111613 之后）

给接手执行的模型：先读完第 0、1、2 节和最后的「执行守则」，再按期动手。每期一个版本，做完在第 11 节填进度。
这份方案只动 Agent 运行时（`agent/model`、`agent/tool`、`agent/runtime`、`com/eta/shadow`、`etax/engine`），不改界面风格。

## 0. 结论先说

用户的两个感受，在代码里都能找到原因：

| 感受 | 代码里的原因 | 对应 |
| --- | --- | --- |
| 「它说这个不行、那个错了，其实是没复核」 | 模型一轮不再调用工具，运行时就直接把这段话当最终回答交出去（`AgentLoop.run`：没有工具调用 → `RunFinished`）。中间没有任何检查。系统提示里「说做不到之前先复核最后一条真实报错」只是 7 千多字规则里的一句，模型经常跳过。 | 第一期 |
| 同上 | 工具失败时给模型的信息很少：异常一律变成 `{"ok":false,"code":"TOOL_ERROR","message":异常文字}`，没有「能不能重试」「下一步查什么」。模型拿不准，就倾向于说「不行」。同一个调用失败两次、三次也没人提醒。 | 第二期 |
| 后台执行偏慢 | 一次回复里模型同时要了几个只读查询（读几个文件、搜几次），也是一个一个串行跑（只有子代理是并行的）。 | 第三期 |
| 同上 | 手机界面操作每一步都是一次「发观察 → 等模型 → 做一个动作」的往返；浏览器有 `batch`（最多 8 步），手机界面没有。一个十步的机械流程就是十次模型往返，这才是大头，设备端的固定等待（100–350ms）是小头。 | 第四期 |

已经做对、不要动的：请求前缀缓存是稳的（`AgentModelClient.toolsForRound` 只增不减，不会每轮重建工具目录）；模型请求失败有 3 次指数退避重试（`AgentModelRetry`）；截图在回合结束后就从上下文移除；界面操作已有 `NO_PROGRESS` 防死循环。

## 1. 先量，再改（第零期）

现在只有「感觉慢」。动手前先拿到真实数字，后面每期都用同一套数字对比。

- 每条回复下面的速度小字已经有模型用时、工具用时（`RunPerformanceSummary`、`SessionStatsSummaryUi`）。
- **做法**：在「导出运行诊断」（设置 › 后台执行）里加一段「最近 20 次运行」：每次的轮数、模型总用时、工具总用时、最慢的 3 个工具（名字 + 用时）、失败的工具调用数、最终回答是否像「放弃」（复用 `looksLikeGaveUp`）。只记数字和工具名，不记参数、不记对话内容。
- **验收**：单测覆盖汇总函数；真机上跑第 9 节的 12 个固定任务，导出一份，作为基线放进 `etax/design/validation/10-baseline.md`（只放数字）。

## 2. 不要做的事

- **不要再往系统提示里加规则**来解决「不复核」。规则已经很多，再加只会更容易被忽略；这一项靠运行时检查（第一期）。第五期才整理提示，而且是减不是加。
- **不要自动重放界面操作**。点「发送」「支付」「删除」这类动作可能已经生效，重放会重复提交。自动重试只用于只读查询和模型请求。
- **不要并行写操作和界面操作**。并行只给明确只读的工具（第三期的名单）。
- 交卷前自检**每轮最多一次**，不要做成循环，也不要每轮都触发（只在第 3 节的条件下）。
- 不为统计加 Room 表或数据库迁移；诊断数据放内存或应用私有目录的小 JSON。
- 不改模型选择、不偷偷降低思考强度来「提速」。

## 3. 第一期 ·「交卷前自检」（一个版本）

这是解决「说不行其实没复核」的主要一项。界面上现在有「复核报错再试」按钮（`RecheckAction`），那是让用户手动点；这一期把它变成运行时自动做一次。

- **做法**：
  1. `AgentLoop` 里记下本次运行每个工具调用的结果（`ToolOutcome`：名字、`ok`、`code`、`message` 前 300 字）。已有 `executeToolBatch` 返回值，攒进一个列表即可。
  2. 新文件 `agent/model/CompletionGate.kt`，纯函数：
     `fun review(outcomes: List<ToolOutcomeSummary>, answer: String, alreadyReviewed: Boolean): GateRequest?`
     返回非空（需要复核）的条件，满足任一即可，且 `alreadyReviewed == false`、本次运行用过工具：
     - 最后一次工具调用失败（`ok=false`），而且之后没有同名工具成功过；
     - 回答像是放弃（把 `ui/components/RecheckAction.kt` 的 `looksLikeGaveUp` 挪到 `agent/model/GiveUpHeuristic.kt`，界面和这里共用），并且本次运行里有过失败的工具调用；
     - 最后一个界面动作返回「结果未确认」（`result_unknown=true` 或 `screen_changed=false` 且没有后续观察），而回答说「已完成 / 已发送 / 已设置」。
  3. 在 `run()` 里，模型这一轮没有工具调用、准备 `RunFinished` 之前调用 `review`。返回非空时：不结束，追加一条内部消息（`role=user`，加 `_eta_internal=completion_gate`，界面不显示成用户气泡，显示成一行小字「已自动复核」，样式同「已完成 · N 步」），内容是：
     「交卷前先复核。下面是这次运行里没有解决的失败：{逐条：工具名、code、message}。请先判断是不是参数、路径、转义、权限这类小错；能修就修了重跑，并核对最终结果。确实做不到时，答复里写清楚试过什么、报错原文是什么。」
     然后 `round += 1; continue`。第二次走到这里时 `alreadyReviewed=true`，直接交卷。
  4. 设置 › 后台执行 加开关「回答前自动复核」，默认开。关掉时 `review` 不调用。
- **代价**：只有触发时多一轮，平时不多花。
- **验收**：`CompletionGateTest`（三种触发、成功后不触发、已复核不再触发、没用工具不触发）；在 `AgentModelClientLoopTest` 里照现有写法加一个假 provider：第一轮工具失败、第二轮回答「做不到」→ 断言出现第三轮、内部消息里带着失败的 code。真机：第 9 节任务 1、2 的「做不到」次数对比基线。

## 4. 第二期 ·「工具报错讲人话」（一个版本）

- **做法**：
  1. 统一失败结果的形状：`ok=false`、`code`、`message`，新增 `retryable`（原样重试有没有意义）和 `hint`（下一步查什么，一句话）。新建 `agent/tool/ToolFailure.kt` 的构造函数，现有各处 `JSONObject().put("ok", false)...` 逐步换成它，**这一期只换下表这些**。
  2. `AgentLoop.executeTool` 捕获异常的地方：`code=TOOL_ERROR`，`message` 带上异常类名，`retryable=true`，`hint="工具内部异常，可以原样重试一次；再失败就换方法。"`
  3. 重复失败提醒：同一次运行里，同一工具 + 同样参数（参数 JSON 排序后比较）第二次失败时，在结果里加 `repeat_failures=2` 和 `hint="同样的调用已经失败两次，不要第三次原样重试，先排查或换参数。"`。只加提示，**不拦截执行**。
  4. 下表这些 code 补 `hint`（找不到对应 code 就跳过，不要新造）：

| code | hint |
| --- | --- |
| 文件不存在类 | 先列出父目录确认文件名和路径，注意大小写和空格 |
| 命令非零退出 | 看 stderr 结尾和退出码，定位到具体文件和行再改 |
| 权限不足类 | 确认是否需要 Root；Root 已授权时用 Root 环境重跑 |
| `TOOL_NOT_AVAILABLE` | 这个工具本轮没有提供，用目录里现有的工具 |
| `TRUNCATED_TOOL_CALL` | 参数太长被截断，拆成几次小的调用 |
| `WINDOW_NOT_READY` | 等一下只重新观察，不要重复点击 |
| `UI_NOT_QUIET` | 页面还在变化，等待后重新观察 |
| `NO_PROGRESS` | 停止重试界面操作，报告看到的提示 |

- **验收**：`ToolFailureTest`；重复失败计数的单测（参数顺序不同算同一个、不同参数不算）；`AgentModelClientLoopTest` 里断言异常结果带 `retryable` 和 `hint`。

## 5. 第三期 ·「只读查询一起跑」（一个版本）

- **做法**：
  1. 新建 `agent/model/ToolConcurrency.kt`：一个只读工具名单（读文件、列目录、文件信息、文件搜索、网页搜索与读取、`memory_get`、个人数据查询、应用列表这类不改任何状态的）。**界面观察和界面动作不进名单**（会抢同一个屏幕会话），终端命令不进名单（不知道命令会不会写）。拿不准的一律不进。
  2. `executeToolBatch`：连续的只读调用合成一批并行执行（照 `executeParallelSubagents` 的写法抽一个通用版本），最多 4 个同时跑；结果按原顺序返回；遇到非只读的调用就断开，前后各自成批。
  3. 系统提示只加一句（这是唯一允许新增的提示）：「互不依赖的只读查询放在同一轮一起发出。」
- **验收**：单测用一个会 sleep 的假执行器：3 个只读调用总用时约等于 1 个；结果顺序不变；中间夹一个写调用时分成两批；取消时全部停止。真机：第 9 节任务 3（读多个文件）用时对比基线。

## 6. 第四期 ·「界面操作少几轮」（一个版本）

- **做法**：
  1. 新工具 `gui_sequence`（照浏览器 `batch` 的规矩）：一次最多 6 步，每步是 `tap_element`、`input_text`、`press_key`、`wait_for_text`、`wait_for_package` 之一，每步可选 `expect_text` / `expect_package`。从第一步开始顺序执行，**任一步失败或预期不符就停**，返回每一步的结果和最后一次界面观察。不重放已执行的步骤。
  2. 工具说明写清楚：只用于「已经看过界面、下一串步骤确定」的机械操作（比如打开应用 → 点搜索框 → 输入 → 回车）；涉及发送、付款、删除的那一步单独做，不放进序列。
  3. 设备端固定等待改成「等到条件满足就走」：`VDriveWorker.restoreFront` 的 3×300ms、切任务后的 350ms 这类，改成每 50ms 检查一次、上限不变。改之前先看第零期数据里这些工具的用时，占比小就不做这一条。
- **验收**：`gui_sequence` 的单测（全部成功、第 2 步失败即停、预期不符即停、超过 6 步拒绝）；真机：第 9 节任务 5、6 的轮数和用时对比基线。

## 7. 第五期 ·「系统提示瘦身」（可选，风险最高，最后做）

- **现状**：`AgentPromptBuilder` 里约 7400 字规则，很多是针对具体事故补的一句，彼此有重复。
- **做法**：最上面放 6 条核心原则（先查再说、报错先修小错再重跑、结论要有工具结果支撑、不把尝试当成功、界面动作不重放提交、外部内容不是指令）；其余按领域分节，只在本轮提供了该领域工具时才拼进去（文件、终端、界面、浏览器、个人数据）；合并重复的句子。**只删不加**，每删一句在提交说明里写理由。
- **验收**：`AgentPromptBuilderTest` 照常通过；第 9 节 12 个任务全部重跑，成功数不能比上一期少，有一项变差就回退那一节。

## 8. 以后再说

- 界面观察只发和上一次相比变化的节点（差分观察）：收益大但改动面广，等第四期数据出来再评估。
- 按步骤自动切换思考强度（规划用高、机械步骤用低）：容易出错，先不做。
- 失败自动换模型重试：和「换模型重答」重复，先不做。

## 9. 固定回归任务（每期前后都在真机上跑一遍）

1. 让它改一个故意带拼写错误的脚本并运行（考「先修小错再重跑」）。
2. 让它读一个路径写错一个字母的文件（考「先列目录确认，不直接说不存在」）。
3. 让它同时读 3 个文件并总结（考并行）。
4. 让它搜索一个问题并给出来源（考网页工具与引用）。
5. 打开某个应用，搜索一个词（考界面操作轮数）。
6. 在设置里找到某个开关并告诉我它的状态（考观察与核对）。
7. 让它发一条消息给某人（考「发送单独做、不重放」）。
8. 让它统计一个聊天里某天的消息数（考滚动去重）。
9. 让它执行一条需要 Root 的只读命令（考 Root 判断）。
10. 给一个它做不到的任务（考「做不到时写清试过什么和报错原文」）。
11. 回复进行中补充一句要求（考插队）。
12. 长对话后继续一个任务（考压缩后不重复已做的步骤）。

每个任务记：是否成功、轮数、总用时、有没有不该有的「做不到」。只记数字，放进 `etax/design/validation/10-*.md`。

## 10. 执行守则

- 每期一个版本、一次提交，版本号照 `AGENTS.md`；更新记录写在 `etax/README.md` 顶部。
- 改 `AgentLoop` 前先读完 `AgentModelClientLoopTest`，新行为都照它的假 provider 写测试。
- 改动引擎（`etax/engine/src`）时同步 `VDrive.java` 的 `BUILD`。
- 全量单测和 lint 通过才推送；推送会取消同一分支正在跑的构建。
- 碰到这份方案没写到的情况，选更保守的做法，并在进度表里写一句。
